# MikroTik Script Compiler Contract

## Architecture invariant

For the MikroTik domain, authoritative RouterOS facts come from two places only:

1. the synchronized/current official MikroTik knowledge package;
2. observed state and verification evidence read from the target RouterOS device.

An AI model is **not** a RouterOS syntax authority and is **not** a source of device facts.
Its role is limited to understanding operator intent, explaining decisions, and proposing an ordering for immutable command primitives that were already generated by deterministic MikroTik renderers.

```text
operator intent
    |
    v
RouterOS discovery -------- official MikroTik offline KB
    |                              |
    +-------------+----------------+
                  v
         deterministic policy / renderer
                  |
                  v
       immutable command primitives
       command_id + section + risk
                  |
             dependency graph
                  |
       +----------+-----------+
       |                      |
       v                      v
 deterministic sort     optional AI sort
                              |
                     command IDs only
       |                      |
       +----------+-----------+
                  v
        deterministic validation
                  |
                  v
        immutable CLI re-assembly
                  |
                  v
             .rsc + SHA-256
                  |
                  v
       import verbose=yes dry-run
                  |
            PASS / FAIL
             |       |
             |       +--> BLOCK
             v
         approval hash
                  |
                  v
            safe execution
                  |
                  v
        read-back verification
                  |
                  v
 official-reference pre/post comparison
                  |
                  v
       backup + handover package
```

## AI ordering boundary

The model receives no RouterOS command strings. It receives only:

- `command_id`;
- logical `section`;
- subsystem;
- risk metadata;
- source index;
- mandatory dependency edges;
- RouterOS target version;
- render-plan digest;
- IDs of official knowledge records supporting the contract.

The only accepted AI response fields are:

```json
{
  "ordered_command_ids": ["..."],
  "rationale": "...",
  "knowledge_ids": ["..."]
}
```

The response is rejected when the model:

- adds or removes a command ID;
- duplicates a command ID;
- violates a dependency edge;
- references unapproved knowledge records;
- returns raw CLI, scripts, new parameter values, or other fields;
- attempts to authorize execution.

The deterministic fallback uses a stable topological sort, so AI is optional. Offline operation does not depend on a cloud model.

## Command ownership

RouterOS command strings are owned by deterministic MikroTik renderers/tool schemas. The script planner only reassembles the exact immutable strings by `command_id` after ordering validation. AI text is never copied into the generated `.rsc` command body.

Renderer ordering remains authoritative inside each subsystem. Additional safety dependencies include, where applicable:

- establish the temporary firewall fail-closed staging guard before rebuilding the managed firewall;
- remove/release the staging guard only after the managed firewall is complete;
- prepare VLAN membership/management reachability before enabling bridge VLAN filtering.

## RouterOS script validation

A compiled script is still generation-only. Before it can enter approval/execution it must pass RouterOS import dry-run validation using the generated dry-run command:

```text
/import file-name="<generated>.rsc" verbose=yes dry-run
```

A dry-run error invalidates the script and blocks approval. The deployment must record:

- target RouterOS version;
- source render-plan SHA-256;
- final `.rsc` SHA-256;
- ordered command IDs;
- offline knowledge provenance;
- dry-run evidence.

If any of these change after approval, the previous approval must not be reused.

## Official knowledge as measurement baseline

`reference_measure.py` evaluates explicit evidence keys against rules linked to offline MikroTik knowledge records. It is used both before and after a change.

The comparison reports:

- controls fixed by the deployment;
- controls that regressed;
- controls that remained compliant;
- controls still missing/nonconformant;
- whether the post-change state is ready to proceed to finalization.

The model does not mark these checks PASS. PASS/FAIL/MISSING comes from deterministic discovery/test evidence.

For example, a secure Internet gateway is not complete merely because the script executed. Post-change evidence must demonstrate management-path survival, desired-vs-actual convergence, stateful firewall behavior, WAN-management restriction, LAN Internet reachability, and idempotency.

A Site-to-Site WireGuard deployment additionally requires non-overlapping peer scope, current handshake evidence, bidirectional LAN reachability, local Internet breakout when requested, denial of undeclared VPN forwarding, and idempotency.

## Source-of-truth rule

When sources disagree, precedence is:

```text
observed RouterOS state / runtime evidence
        +
current official MikroTik manual / CLI reference
        >
legacy documentation
        >
AI model prior knowledge
```

AI may point out an inconsistency, but it may not override the deterministic compiler or device evidence to make a deployment pass.
