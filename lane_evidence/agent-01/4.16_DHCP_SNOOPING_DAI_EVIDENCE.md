## Current Controller evidence

Official current guide: `What is DHCP Snooping and DAI and How to Configure Them on Omada Switches When Adopted on Omada Controller` (2026-01-27):
https://support.omadanetworks.com/en/document/115293/?app=t

Cited requirements: Omada Access / Access Plus / Access Pro / Access Max / Aggregation switches with current firmware, and Omada Controller V6.1+.

The guide defines DHCP Snooping and Dynamic ARP Inspection (DAI) as parts of IP-MAC-Port Binding (IMPB). DHCP Snooping learns valid IP/MAC/port/VLAN/lease bindings from DHCP traffic. DAI validates ARP packets against the binding source and drops packets that cannot match a valid entry on DAI-enabled ports. In DHCP networks, DHCP Snooping is a binding source for DAI. For static-IP-only networks, the guide describes using manually added bindings rather than relying on DHCP-learned entries.

The current Controller workflow explicitly warns that the switch cascade port cannot be selected for DHCP Snooping in that workflow, so the switch can obtain an IP address via DHCP. This topology/management dependency must remain an execution gate.

## 2026 CLI evidence

- `ip dhcp snooping vlan <vlan-range>`
- per-interface `ip dhcp snooping max-entries <value>`

- `show ip source binding`
- `show ip dhcp snooping`

The same current CLI reference Chapter 93 documents ARP Inspection including global `ip arp inspection`, validation controls, VLAN scope, trusted ports and operational read-back (`show ip arp inspection`, interface/VLAN/statistics). The guide explicitly calls out uplink/routing/LAG ports as examples that should be trusted before ARP detection is enabled in the cited scope.

## State separation

Keep separate:

- static/manual IP-MAC-VID-port bindings;
- dynamically learned DHCP bindings;
- DHCP Snooping global/VLAN/port/trust state;
- DAI global/VLAN/port/trust/validation state;
- IP Verify Source / source guard state;
- binding table and violation/statistics evidence;
- management/uplink/cascade topology state.

DHCP Snooping is not DAI, and neither silently authorizes IP Verify Source.

## Safety gates

- Snapshot existing bindings before changing protection state.
- Identify DHCP server/uplink/cascade/routing/LAG paths before enabling enforcement.
- Never mark an infrastructure port untrusted by inference.
- Static-IP environments require explicit binding strategy; do not fabricate DHCP entries.
- VLAN scope must be explicit.
- Configuration acceptance is not PASS if expected clients lose DHCP/ARP/IP connectivity or binding/read-back evidence is absent.

## Verification target

PASS requires configuration read-back, correct learned/manual binding table, successful legitimate DHCP/ARP/IP flows, rejection evidence for representative spoof/rogue-server traffic where safely testable, and healthy management/uplink reachability.
