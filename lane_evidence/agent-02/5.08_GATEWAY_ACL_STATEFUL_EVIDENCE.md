## Current official evidence

- `How to Implement Unidirectional VLAN Access Through ACL Configuration on the Omada Gateway in Controller Mode`, 2026-08-31: https://support.omadanetworks.com/in/document/13151/
- `How to Configure Gateway ACL on Fusion Gateway`, 2026-07-23: https://support.omadanetworks.com/nordic/document/121370/
- Current Gateway ACL examples surface, 2026-06-23: https://support.omadanetworks.com/en/document/13189/

The 2026 stateful/unidirectional example shows that stateful Gateway ACL can block IoT-to-LAN initiation while retaining LAN-to-IoT access in its cited topology. This behavior is example/device/controller scoped and must not be generalized to every gateway/firmware.

The current Fusion Gateway guide states rules are evaluated sequentially and first-match determines accept/drop; later rules are not checked. Rule order is therefore part of desired state, not display metadata.

## State planes

- ACL enable state
- ordered rule list
- source selector
- destination selector
- protocol/application/port selector
- permit/deny action
- stateful/state-type behavior where supported
- time-range binding
- device/client/group binding
- hit/traffic verification

## Safety

- Never reorder ACL rules silently.
- Do not assume stateful semantics exist on a model merely because another current guide demonstrates them.
- Broad deny rules require explicit management/Controller/DNS/DHCP/gateway reachability analysis.
- ACL is separate from NAT, routing/PBR, VLAN segmentation and client isolation.
- An implicit/default policy must be sourced for the exact mode/version before the compiler depends on it.

## Verification target

PASS requires rule read-back in exact order plus positive/negative flow tests: intended denied initiation fails, intended permitted/reply traffic succeeds, and management/Controller paths remain healthy. Apply success alone is EXECUTED_UNVERIFIED.
